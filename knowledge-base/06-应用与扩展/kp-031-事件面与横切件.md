# 事件面与横切件

## 一句话定义
围绕核心循环的"件"：jobs（带输出环的后台任务 + `job_*` 工具）、schedule（Host 级提醒，独立于会话激活）、hooks（复用 Claude Code/Codex 的 hooks.json）、webhook（fire-and-forget 可信回调 → 开会话）、todo/plan（log-only 的软引导状态），加上身份/凭据/设置/存储/工作区五个支撑包。

## 为什么重要
这些横切件展示了同一套模式的反复应用：**log-only 事件 + 投影 + Remote 面 + 模型工具**。学会这个模式，你就能预测任何新子系统的形状。

## 前置知识
kp-016（log-only 事件）。

## 核心概念

**jobs**（jobs/jobs + jobs-local + tool-jobs）：
- `JobId = <kind>-N`（`JobKindMap{bash,subagent}` merge-extensible）；`JobStatus = running|stopping|completed|killed|failed`；
- Producer 提交 `JobSpec{kind,label,owner?,outputLimitBytes?,run(job)=>JobHooks}`；runtime 负责 identity/访问围栏（owner session）/生命周期/输出 ring；
- 结算 first-wins；`dsh-tool-jobs` 把结算转成 in-session notice——模型用 `job_output/job_list/job_kill`，无需轮询；
- Host 面 `ctx.jobController` 提供 `@Remote({mode:'stream'}) list`（whole-set 帧）与按字节偏移的输出流。

**schedule**（schedule/schedule）：Host 级提醒，**独立于 Session 激活存储**，到期投递回原 Session（必要时恢复它）；storage domain `tasks` 表，kind：after/at/every/daily/weekly/cron（RFC3339 UTC + 显式 IANA timeZone）；投递 ack 是 inbox admission（不是模型执行完成）；漏掉的 recurring 只补最新一次；payload-free `schedule/changed` 事件让客户端列表失效。模型工具 `schedule_create/list/delete/update`。自 2026-09-25 起以**可选 bundle** 发售：`time-context / schedule / ui-schedule` 三行移出 Web 组合、由 bundle 插入（`dsh.bundle.rowSwitches: false` 使 bundle 自身开关成为唯一控制，Plugins 页按 bundle 归组）。

**hooks**（hooks/）：复用现有 **Claude Code / Codex 的 hooks.json**（`hook-protocol` 共享引擎 + 两个桥插件）；只有 command hook 会跑（http/mcp_tool/prompt/agent 跳过并告警）；**exit 2 阻断** prompt/tool call 且 stderr 成为模型可见原因；返回附加 context 进下一请求。

**webhook**（webhook/webhook + webhook-github）：fire-and-forget——`ctx.webhookRuntime.register(rule)` 注册可信回调，dispatch 独立调度、**回调 settle 前返回**；无队列/重试/去重/崩溃重放；内置唯一动作 = Workspace 支撑的 Session 创建（以 `source.kind:'webhook'` 注入 user 消息）；GitHub adapter 验签原始 body、内存 dispatch 后立即 202。

**todo / plan**（log-only 软引导）：
- todo：`TodoItem{content, status}`，工具 **整表替换**（last-write-wins，无 id）；`todo/write` 为 log-only 事件 + replay 投影 + invariant companion；
- plan mode：`ctx.planMode`；log-only `plan/mode {active}` + `plan` 投影；激活注入 `plan:policy` section（order 50）；`exit_plan_mode` 经 user-questions 呈现计划评审（approval→silent pending exit；keep-planning→携反馈失败的调用）；**是软引导，与 sandbox/approval 独立**。

**支撑五包**：
| 包 | 职责 |
|---|---|
| identity/anonymous-user-id | 每 home 一个匿名 id，附加遥测/反馈/DeepSeek 请求——可识别安装不可识别用户 |
| credentials | 配置只写凭据名不写值；credentials-local 私有 YAML 存储，环境变量覆盖优先；authorization 管理向人要凭据的流 |
| settings | 编辑插件声明 `.volatile()` 的配置项（Config 派生表单）；秘密值只给 presence marker；持久化走 profile patch |
| storage | 非会话持久化 hub：`ctx.storageDomain` 读写校验过的 record；多 backend 可并存（json/sqlite），domain 配置决定路由 |
| workspace | `ctx.workspaceRegistry`：持久有序的项目目录表 + session 归属（header 校验）、归档（隐藏不删除）；**模型不可见** |

## 直观类比
这一层像 **写字楼物业服务**：jobs=共享打印室（排队、取件码、可叫停）、schedule=前台叫醒服务（哪怕你不住店）、hooks=门禁规则兼容隔壁大楼的卡（Claude Code/Codex）、webhook=前台代收快递（只收认识的寄件人，签收即走）、todo/plan=白板与便签（软约束）、支撑五包=水电物业/身份登记/储物柜。

## 实例 / 案例
- `bash` 工具的 `run_in_background` 走 `ctx.jobs`（kp-021）——长任务不阻塞模型；
- Desktop 退出检查读取 armed reminders（schedule 与桌面生命周期的耦合点）。

## 常见误区
- **以为 webhook 有重试**：明确 fire-and-forget；要可靠投递请自己接队列；
- **以为 plan mode 是权限机制**：log-only 软引导，sandbox/approval 才是硬边界；
- **在 credentials 里存明文**：配置只允许凭据名（ref），值走 ctx.credentials 存储。
