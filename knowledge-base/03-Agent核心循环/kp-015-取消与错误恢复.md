# 取消与错误恢复的完整语义

## 一句话定义
dsh 的取消是 **带因果的信号传播**（cause 归一为 user/parent/hook/disposed），贯穿"请求前/流中/工具中"三个阶段，且每个阶段都有明确的不变量（该提交的提交、该丢弃的丢弃）；进程崩溃后由 resume 的合成闭合器把开放尾巴修成合法日志。

## 为什么重要
长任务 Agent 必然被取消/崩溃。取消语义不清的 harness 会出现"幽灵工具调用"或"半个 assistant 消息"这类脏状态；dsh 用因果 + 结算 + 合成闭合三件套把脏状态压到零。

## 前置知识
kp-010、kp-013、kp-014。

## 核心概念：三阶段取消

| 阶段 | 行为 | 不变量 |
|---|---|---|
| `agent/request` / `prepareCall` 异步期 | abort | **system 与 users 都不提交**（cancellation commits neither） |
| 流式中 | abort | 已 start 且有可见前缀 → `assistant/message{interrupted:true}`；无前缀 → `assistant/attempt` |
| 工具已启动 | abort | 进行中调用排空按序提交；未启动调用获得合成 `tool/call` + 错误 `tool/result`（`ABORTED_BEFORE_DISPATCH`） |

**Cause 归一**（agent.ts:80-95）：`{user|parent|hook|disposed}` 的拷贝进入 `turn/end{kind:'aborted', reason}`；`cancel(cause,{keepInbox})` 默认清空 inbox 并 abort loop 拥有的 AbortController（:175-181）。

**失败 step 的就地结算**（2026-09-19 决策，477b4f42→21638c56 窗口合入）：step 因错误关闭前，驱动器为每个未回应的 assistant tool call 记录错误结果——已落 `tool/call` 记录的得 `TOOL_OUTCOME_UNKNOWN`（文案 "Its outcome is unknown."，仅允许重试只读/幂等操作）；连开始记录都没有的得 `TOOL_NOT_STARTED`。已提交的结果保持原样、已启动的 dispatch 先结算再恢复；turn 保留原始失败原因。这让后续请求拿到配对的工具历史，而不会自动重试有副作用的操作；且失败 step 恢复**不重写**已关闭历史回合中的未回应调用。architecture.md 为此增补一行 "Failed steps record missing tool results"。

**崩溃尾巴恢复**（repair.ts）：resume 时 `interruptedTurnClosers(log)` 为开放尾巴生成合成 closers（与上一条共用同一套闭合语义）：
- 未决 tool call → `TOOL_NOT_STARTED` / `TOOL_OUTCOME_UNKNOWN` 错误结果（同上语义，repair.ts:35-44）；
- 补 `step/end` → `turn/end {kind:'interrupted'}`；fork 切点用 `{kind:'forked'}`；
- 时间戳复用最后真实事件，seq 顺延——日志的 seq 连续性契约不破；恢复路径同时容忍"无 pending 的 tool/result"（本窗口修复）。

## 原理 / 机制：为什么"合成事件"不算撒谎
合成 closers 只描述 **从日志可证明** 的事实（"这个 call 没有落 result"→ 结果未知），不伪造成功；文案明确告诫恢复者。这延续了"model-visible means logged"的保守取向：宁可标注未知，不可编造历史。

## 直观类比
像 **核电站的 SCRAM 按钮**：按下（abort signal）后分阶段处置——燃料加注前（prepareCall 期）直接停线（什么都不提交）；反应中（流式）封存已产出并记录中断；外运中（工具）已在途的运完、未发车的回库登记"未发车"（合成事件）。事后审计（resume）补写事故报告（closers），但只写可证实内容。

## 实例 / 案例
1. 用户按停止 → `turn/end{reason:'aborted', cause:'user'}`；UI 收到 `agent/status` idle；
2. 断电崩溃 → 下次 resume：日志尾部 open turn 被补上 `interrupted` 闭合，agent 从干净边界继续；
3. 派生 agent 父级取消 → cause='parent'，传播到子 agent 的 turn/end。

## 常见误区
- **以为取消 = 立即 everything 回滚**：工具在途结果会被提交（已发生的事实），只丢"未开始的"；
- **以为 resume 静默修复**：合成结果带警示文案，恢复策略由用户/插件决定；
- **在插件里自建 AbortController 而不看 `ev.signal`**：会与 loop 的取消时序脱节。
