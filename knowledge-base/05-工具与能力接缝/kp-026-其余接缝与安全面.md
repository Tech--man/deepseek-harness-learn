# 其余接缝与安全面

## 一句话定义
执行世界之外的六块拼图：MCP（外部工具桥接 + 资源只读工具）、skill（frontmatter 定义 + catalog 注入 + 按需加载）、browser-use 与 computer-use（每实例恰一 provider 的浏览器/桌面操控）、PTC runtime（`run_code` 沙盒程序化调用工具），以及贯穿一切的审批与安全策略（fail-closed）。

## 为什么重要
这些是 Agent"伸出手"的其余方向，也是生态扩展最活跃的层；审批与 SAFETY 则是 dsh 对"能干活的 Agent"的伦理回应。

## 前置知识
kp-021、kp-023。

## 核心概念

**MCP**（mcp/）：`mcp-client` 每 server 一连接；公共工具名含 `serverName` 前缀；server instructions 进 system prompt（MCP_SERVERS order 3100）；`mcp-resources` 提供只读资源工具 `list_mcp_resources / list_mcp_resource_templates / read_mcp_resource`。

**skill**（skill/skill + tool-skill）：
- 定义 = `SKILL.md`（YAML frontmatter + Markdown body）；语义键 `name/description/whenToUse`，策略键 `disable-model-invocation`、`user-invocable`（缺省 true）；
- 发现 rank 表（skills.md:83-91）：`.dsh/skills` 100 → `.agents/skills` 200 → custom 300 → `~/.dsh/skills` 400 → `~/.agents/skills` 500 → bundled 600；目录 bundle 或平文件，kebab-case；
- 注入两段式：会话前缀以 `catalog`-form context 经 `agent.inject()` 发 user/message（位置在 catalog 区）；模型调 `skill` 工具加载完整 body → 作为 pre-step 注入 instructions，**排 catalog 之后**保证位置确定；目录变更发替换目录（update:true）。

**browser-use / computer-use**：`ctx.browserUse`（stagehand_act/extract/navigate/observe/screenshot/tabs…；providers: playwright-mcp / chrome-devtools-mcp / stagehand-native）与 `ctx.computerUse`（cua-driver-mcp / native）；服务只管注册，**每实例恰一 provider**，浏览器归属 exact Agent+Session。

**PTC runtime**（ptc-runtime）：`PtcRunRequest{program, bindings, cwd, timeoutMs, sandboxPolicy, signal}`——程序是 async 函数体，`bindings` 是宿主函数命名空间；默认 provider 沙盒 Node（ptc-runtime-node）。`run_code` 保留名 + `mode: ptc|both`：子调用以 bindings 重入完整守卫管线（kp-021）；`tool/ptc-dispatch` log-only，落盘副本可被 waterfall 改写（spill preview），程序拿完整值。

## 原理 / 机制：审批与安全

**approval**（interaction/user-approval）：
- `ApprovalOutcome` 闭集 `allowed-once | rejected | cancelled | unavailable`，**fail-closed**：无 answerer/抛错/非法返回 → 归一 `unavailable`（=拒绝）（index.ts:282-291）；
- per-session 策略 `ask | never`；生效值 = 会话日志最后一条 `approval/policy` 事件；`never` 在派发前确定性拒绝（CI/headless 姿态）；
- `approval/request` 是 Agent-scoped waterfall（只收本 agent 的请求）；`approval/asked + decided` 是 log-only 审计对；模型只见工具结果与策略，不见 UI/审计。

**permission-presets**（permission-presets/src/index.ts:63-117）：`workspace-write / danger-full-access` 用户预设，每个捆绑 sandbox mode + approval policy 两个 knob，一次切换写两条 knob 事件——"权限=沙箱+审批"的捆绑器。

**UI 呈现**（client/ui-approval）：经 Agent-scoped Remote waterfall 收 pending 请求 → 发布到 `ctx.uiSession`、**接管 Conversation composer**、可关联渲染工具详情；键盘 Enter=approve / Esc=reject；仅 allow-once/reject（持久策略归 Host 侧）。

**SAFETY.md**：仓库要求运行前阅读；模型可执行任意代码的风险、沙箱/审批的双重缓解、以及"权限策略是日志事件"的可审计性。

## 直观类比
- MCP = **外聘专家登记处**（每人一块名牌前缀）；
- skill = **图书馆的索引卡**（先给目录，需要时才取书，取了必须放在目录之后）；
- PTC = **手脚的编程接口**：与其让模型一步步说，不如让它写小程序批量调用；
- 审批 fail-closed = **机场安检门的失效模式**：断电（无 answerer）时门保持锁死。

## 实例 / 案例
- Office skills（docx/pptx/xlsx）随桌面捆绑，走 skill 目录 rank 的 bundled 层；
- `exit_plan_mode` 工具经 `ctx.userQuestions` 呈现计划评审（intent: plan-review），`/plan` 命令控制 `plan/mode` 日志事件（kp-031 的 plan 细节）。

## 常见误区
- **以为 approval 是 UI 的事**：Host 侧 seam 是权威；UI 只是 answerer 之一；
- **以为 skill body 会整本塞进提示**：只注入 catalog；body 按需加载且位置确定——提示经济学；
- **以为 browser-use 可以多浏览器并行**：服务端约束每实例一 provider，浏览器归属精确 Agent+Session。
