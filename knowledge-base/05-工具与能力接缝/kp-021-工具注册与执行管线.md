# 工具注册与执行管线

## 一句话定义
工具经 `ctx.tools.register()` 注册（全局或 `agent.ctx` scoped），执行走 **prepare → dispatch → finalize** 三段水瀑管线；并发模型是"按模型顺序分段、段内有界滚动池（默认 10）、段间屏障"，结果严格按模型序提交。

## 为什么重要
工具是 Agent 的手。dsh 把"能不能执行"（守卫）、"怎么执行"（管线）、"何时并行"（executionMode）三个正交问题解耦，且每一段都可被插件拦截——理解它，就理解了所有工具类扩展（bash/fs/MCP/skill…）的公共宿主。

## 前置知识
kp-010（step 内工具段）、kp-007（waterfall）。

## 核心概念

**ToolDefinition**（tools/src/index.ts:223-299）：ToolSchema + 强制 `output {schema, render, presentationMeta?}` + `execute(args, exec)`；可选 `projectContent / finalizeContent / timeoutMs / isConcurrencySafe / presentCall / presentResult`。`run_code` 是保留名，任何 scope 不可注册或遮蔽（:1088-1090）。

**表现模式**：`native | ptc | both`；`presentAs(mode)` 按 scope 声明（agent preset 用它让 PTC 与 native agent 共存）。ptc 模式下模型直呼（无 parent token）只能叫 `run_code`，其余 `UNKNOWN_TOOL`（:1359-1361）。

**executionMode**（:1311-1320）：只有 `resolveExecution` 可见 **且** `isConcurrencySafe(args)` 严格 `=== true` 才是 `parallel`；未知/隐藏/异常一律 fail-closed 为 `exclusive`。

## 原理 / 机制：三段管线（:465-474,1381-1397）

```text
prepare   物化执行对象（参数 lossless JSON 快照并深冻结）
          → tools/pre-execute (waterfall): allow | deny | cancel | ask(需 approval)
          → guards：单调守卫——只能返回拒绝理由，不能把拒绝改回允许（:731-739）
dispatch  tools/execute (around waterfall)：超时/重试/metrics 包装可换 exec.signal
          registry 重新融合 caller signal（:153-176）
finalize  tools/post-execute (waterfall): accept{content?|value|additionalContexts} | block{feedback}
          → definition.finalizeContent → 物化冻结 → emit tools/result
```

**调度器与并发**（tool-calls.ts:60-247）：
1. `executeToolCalls` 按模型顺序分段：读第一个调用的 `executionMode`；`parallel` 时整段其余调用进组（否则单调用=屏障组）；读模式前先提交上一段——registry 变化影响未启动调用；
2. `runGroup` 有界滚动池：`maxParallelToolCalls`（默认 10，volatile 可热改）；`fillPool` 启动每个调用前重读后续 mode，遇非 parallel 即停——**由 registry 变化触发的动态屏障**（:199-214）；
3. 结果与 `additionalContexts` 严格按模型序提交（`commitReady` :147-161）；`tool/result` 用 `sourceEventSeqs:[callSeq]` 引用其 call（:269-290）；
4. abort：已启动调用排空按序提交；未启动调用获得合成 call+result 对（kp-015）。

**guard 注册**：`ctx.tools.guard()`（:1144）——pre-execute 之后的守卫，语义是"收窄不放宽"。仓库自带 `guard/timeout-policy`、`guard/repeat-tool-reminder`。

## 直观类比
三段管线像 **餐厅出餐三岗**：备菜（prepare：验证+预检，可退单可转人工 ask）、炒菜（dispatch：灶台可被包一层计时/重试）、装盘（finalize：可改摆盘、可附加小票、也可整单拦下）。滚动池像 **三个灶眼**（默认 10 个并行）：按订单顺序上灶，遇"必须独占的菜"（exclusive）其他灶等它。

## 实例 / 案例
- `tool-bash` 的执行期沙箱升级：`approveBashEscalation → ctx.approval.request`（tool-bash/src/index.ts:482-483）——发生在 pre-execute 的 ask 分支；
- `tool-fs` 的写前置读：`fs-observation-policy` 通过 `fs/*` 事件强制"写前先读"（kp-025）。

## 常见误区
- **以为并行结果乱序提交**：提交严格按模型序（模型的历史一致性优先于完成时间）；
- **以为 guard 可以"批准"**：单调收窄；放宽只能走 pre-execute 的 allow；
- **在 execute 的 around 包装里丢 signal**：registry 会重新融合 caller signal，但包装者替换 `exec.signal` 必须接住取消。
