# 工程纪律：规则、门禁与测试矩阵

## 一句话定义
312 个工作区包（54 组）能保持架构一致，靠的是 **规则 → 可执行门禁 → CI 聚合** 三层机器：AGENTS.md 写下硬规则（如"registrations are effects""fail loud"），scripts/ 下数十个 `verify-*` 把规则变成可运行的检查，`run-gates.ts` 的 DAG 门图与 20 个 GitHub workflow 把检查编排进 CI。

## 为什么重要
这是"一切皆插件"能活下来的条件：没有特权内核意味着没有天然的收敛点，纪律必须外置成机器。这份工程资产本身就值得整个借鉴。

kp-002（monorepo 地图）。

## 核心概念：AGENTS.md 的承重规则（15 条精选）

1. **应用启动唯一通道**：只有 dsh profiles 能启动受支持的 Node 应用（`verify-application-entrypoints` 强制）；
2. **Session 数据世代不可变**：迁移只追加版本命名后继，绝不移动/覆盖/删除已提交世代（kp-017 的规则化）；
3. **Registrations are effects**：一切贡献走 `ctx.effect()/ctx.on()`，`register()` 返回 disposer；
4. **Model-visible ⟺ logged**（kp-016）；
5. **Plugins, not loop changes**：新行为落文档化扩展点；改 agent-loop 必须同步 architecture.md；
6. **Seam 三角色完整交付**；
7. **显式 > 隐式**：默认值必须是 owning 实现里的显式 `resolve(request): Spec`，禁止 `?? default` 藏在 run() 里；
8. **Misconfiguration fails loud**，永不静默跳过缺失 referent；
9. **跨边界 opaque id 必须 branded**（`dsh-brand`），禁止裸 string；
10. **信任 TypeScript**：只在 parser/config、queued、model JSON、durable/file、worker、process、wire 边界做运行时校验；**禁止新增 `as unknown`**（基线只减不增）；
11. **Waterfall 监听者必须调 `next()`**；闭式 union 以 `assertNever` 收尾；
12. **测试描述行为**：改过时行为连同测试一起改；非平凡变化更新 keyless 录制快照；两个 SDK 同 PR 同步；
13. **本地只跑相关检查**：CI 拥有穷尽覆盖与平台矩阵；
14. **严格 TS + 每导出必 JSDoc**（`verify-export-jsdoc`）；
15. **文档字数预算制**：architecture.md ≤2400 词等（`verify-doc-budgets` 拒绝超标）。

## 原理 / 机制

**verify 脚本族**（scripts/，按域分组）：
| 域 | 代表脚本 |
|---|---|
| 架构/应用 | verify-application-entrypoints、verify-runtime-closure、verify-default-product-isolation、verify-cordis-config（`!!js` 只许 disabled 字段）、verify-no-unknown-casts、verify-no-bare-dispatcher |
| 包结构 | check-workspace-constraints（manifest 不变量）、verify-package-dependencies、verify-client-domain-graph |
| 文档（~40 门） | verify-md-links、verify-md-wrap、verify-doc-budgets、verify-type-equiv（文档粘贴的类型与源码一致）、verify-subsystem-pages、verify-translation-pairing（中英配对） |
| 生成物 --check | config/tool/cordis/persistence/session-format/module-graph 等 catalog 的新鲜度门 |
| 覆盖率 | coverage-exempt + coverage-partitions：**per-file 100%** 覆盖率门（含豁免清单与分区机制） |

**CI 策略**：GitHub Actions 20 个 workflow；PR 入口 `ci.yml` 十个 job（静态门/coverage/bench/consumers/node-compat/python/windows 三件套 + 汇总必需检查）；`run-gates.ts`（1660 行）定义 DAG 门图与 16 个模式，对应 `check:*` scripts。GitLab CI 只管 Python runtime wheel 发布（多平台 + glibc/manylinux 校验）。**lefthook 刻意不跑测试**——本地只做 staged lint/翻译配对/空白检查，重活全部留给 CI（"本地只跑相关检查"规则的执行）。

**测试矩阵**：
| 车道 | 内容 |
|---|---|
| `test` | 单元主车道；per-file 100% 覆盖率门 |
| `test:e2e` | 真 API（无 key 自跳过） |
| `test:snapshot` | **录制会话回放**：keyless 默认 replay，diff 组装请求/协议输出/持久化日志 |
| `test:web` | 浏览器车道：真实宿主入口 + built-client 交互快照 |
| `test:bench:built` | 性能门：benchmarks/（流重连 63ms 预算、长会话打开、终端 IO 保留窗口…） |

**TS 双聚合布局**（docs/development.md）：Host 与 Client 两个隔离聚合编译——两侧对 cordis `Context` 的同名 declaration merge 会在单一 Program 内冲突；共享叶子显式登记。这是 monorepo 修 TypeScript 的实战教科书。

## 直观类比
这套机器像 **机场的适航体系**：手册（AGENTS.md）→ 检查单（verify-*）→ 定检计划（CI 门图）；地面只做绕机检查（lefthook），大修全部进机库（CI）。

## 实例 / 案例
想看规则如何长在代码里：`grep -r "as unknown" packages/ | wc -l` 后读 `verify-no-unknown-casts.ts` 的基线机制——存量只减不增，新增即失败。

## 常见误区
- **以为规则只是文档**：几乎每条规则都有对应 verify 门；
- **以为本地该跑全套**：lefthook 刻意轻量，全量是 CI 的职责；
- **把 AGENTS.md 当"AI 提示词"**：它同时是人类贡献者的宪法（`CLAUDE.md` 是其符号链接）。
