# 时空可组合编程范式：Cordis 论文的定位

## 一句话定义
dsh README 开篇指明其架构出自 Cordis，而 Cordis 的设计文档是论文《A Programming Paradigm for Spatiotemporal Composability》（arXiv 2608.25512）——主张以"服务 + 类型化事件 + 可逆 effect"实现 **时间轴上（生命周期）与空间上（插件树）都可组合** 的软件构造法。

## 为什么重要
理解范式层的意图，才能解释 dsh 的一堆工程规则为何如此设计（为什么注册必须可回收、为什么事件是扩展点、为什么 patch 永不跨层）。这是"从看懂代码到看懂设计"的阶梯。

## 前置知识
kp-002（dsh 地图）；对插件式架构的一般经验。

## 核心概念：三个可组合轴

| 轴 | 含义 | Cordis 中的体现 |
|---|---|---|
| **空间可组合** | 功能分布在插件树中，任意节点可增删 | Context 树：每个插件是树上一个 fiber 节点，子 Context 继承父服务 |
| **时间可组合** | 功能在运行时随生命周期进出 | 挂载/卸载（mount/unmount）随时发生，注册即 effect，卸载自动回滚 |
| **类型可组合** | 服务与事件跨插件类型安全 | TypeScript 声明合并：`interface Context { tools: ToolRegistry }`、`interface Events { 'tools/execute': ... }` |

（注：论文本身需要单独阅读；本知识点以 dsh 仓库内的落地为准——`docs/cordis-primer.md` 是官方实操浓缩版，`vendor/cordis/src/` 共 9 个文件是全部机制。）

## 原理 / 机制：范式如何约束 dsh

1. **"注册即 effect"** —— 任何插件在挂载期做的注册（`ctx.on`、`ctx.effect(fn)`）都必须返回/持有 disposer，Context 卸载时按逆序回滚。这解释了 dsh 的事件回调几乎从不手动移除。
2. **"事件是扩展点，服务是能力"**（docs/cordis-primer.md:43-45）—— 拦截/策略走事件（waterfall 可以改变结果），直接调用走 service 方法。两者的边界是 dsh 事件域划分的依据（session/agent/capability 三域）。
3. **"依赖注入等待"** —— `inject: ['tools']` 让插件在服务齐备前保持 PENDING；配置求值也被推迟到依赖激活后（`!!js` 表达式，vendor README 修改 15）。时间组合因此是"就绪驱动"而非"顺序驱动"。
4. **"分层补丁而非继承"** —— 组合的每一层只能整块替换配置行，不能深入改上一层的内部逻辑，保证上层补丁始终可预测。

## 直观类比
把软件想成 **即兴爵士乐** 而非交响乐：乐手（插件）随时上下台（时间组合），舞台分区（Context 树）决定谁能听见谁（空间组合），乐谱类型（声明合并）保证互相听得懂（类型组合）。指挥不预先写死每一位乐手——只定规则。

## 实例 / 案例
dsh 的 300 余个包中没有任何一个被"硬编码"进内核：`dsh-base` 只是一份单次 insert 的 YAML patch（529 行 / 94 个插件行），把插件行一次性插到空 entry 列表上；用户在 home 层加一个 `- id: agent-loop / disabled: true` + 自己的替代实现行，就完成"换循环"。

## 常见误区
- **把 Cordis 当 DI 容器**：它不止注入——事件系统（5 种派发模式）与 effect 生命周期才是主菜；
- **以为论文必须先读**：`docs/cordis-primer.md`（45 行）+ `docs/cordis-tutorial/`（7 章实操）已覆盖落地所需；论文是加深理解的可选材料；
- **以为 vendor 是"抄来的代码"**：内嵌是为锁版本与打补丁（22 条修改，含重入回收加固、`applyEntryPatches` 导出等，vendor/README.md:29-57）。
